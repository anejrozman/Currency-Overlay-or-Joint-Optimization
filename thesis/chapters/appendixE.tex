\section{The CVXPY Library}\label{sec:cvxpy}

All optimization problems in this thesis are implemented with CVXPY, an open-source, Python-embedded modeling language
for convex optimization problems \cite{DiamondBoyd2016}. It lets us express a problem in a natural way that
follows the mathematics, rather than in the restrictive standard form required by solvers, and it automatically
transforms the problem into standard form, calls a solver, and returns the results in a readable format \cite{CVXPYDocs}. CVXPY 
acts as an interface between the problem written in Python and an external numerical
solver, which in this thesis is the Gurobi solver. In this section, we summarize the parts of
the CVXPY library needed to understand the implementation of the programs. Further details can be found in the CVXPY documentation \cite{CVXPYDocs}.

In a CVXPY program, variables, created with
\texttt{cp.Variable}, are the decision variables of the problem and can be scalars, vectors, or matrices. Parameters,
created with \texttt{cp.Parameter}, are symbolic representations of constants, whose purpose is to change the value of a
constant in a problem without reconstructing the entire problem. Variables, parameters, and numerical constants are combined into
expressions through the usual arithmetic operations and a
library of functions called atoms, such as \texttt{cp.sum}, \texttt{cp.norm}, and \texttt{cp.sum\_squares}. 
An objective, \texttt{cp.Minimize} or \texttt{cp.Maximize} of a scalar expression, and a list of
constraints then define a problem \texttt{cp.Problem}. Calling its method \texttt{solve} returns the optimal value and stores
the optimal solution in the attribute \texttt{value} of every variable.

\Cref{lst:cvxpy-least-squares}, adapted from the CVXPY documentation, illustrates these objects on the least-squares
problem with the constraint that the solution lies in the unit box
\begin{equation*}
    \min_{\bm{x}} \ \|\bm{A}\bm{x} - \bm{b}\|_2^2, \quad \text{s.t. } \bm{x} \in [0,1]^n,
\end{equation*}
for a matrix $\bm{A} \in \mathbb{R}^{m \times n}$ and a vector $\bm{b} \in \mathbb{R}^m$, in this example drawn at random with
$m = 30$ and $n = 20$. Lines 5--8 of the code generate the problem data and line 11 declares the variable
$\bm{x} \in \mathbb{R}^n$. Line 12 states the objective with the atom \texttt{cp.sum\_squares}, line 13 the two
elementwise constraints, and line 14 combines them into a problem. Line 17 solves the problem with Gurobi set as the solver, and line 18 prints the 
optimal solution stored in \texttt{x.value} as a NumPy array. 

\begin{lstlisting}[style=python, caption={Least-squares problem with box constraints in CVXPY, adapted from the CVXPY documentation \cite{CVXPYDocs}.}, label={lst:cvxpy-least-squares}]
import cvxpy as cp
import numpy as np

# Problem data.
m = 30
n = 20
A = np.random.randn(m, n)
b = np.random.randn(m)

# Construct the problem.
x = cp.Variable(n)
objective = cp.Minimize(cp.sum_squares(A @ x - b))
constraints = [0 <= x, x <= 1]
prob = cp.Problem(objective, constraints)

# Solve the problem.
result = prob.solve(solver=cp.GUROBI)
print(x.value)
\end{lstlisting}

When \texttt{solve} is called, CVXPY compiles the problem in the steps shown in \Cref{fig:cvxpy-chain}. 
It first checks that the problem is convex using the rules of disciplined
convex programming (DCP). Each variable and function has a
curvature label (affine, convex, or concave), and simple rules combine these
labels as the expression is built. For example, a sum of convex terms is
convex. If the objective and constraints do not end up with labels that make
the problem convex, CVXPY rejects it before any solver is called. The problem is then passed through a chain of reductions. A reduction is a
transformation from one problem to an equivalent one. The reductions
replace each atom that the solver does not accept directly by auxiliary variables and constraints. For example, each
absolute value $|x_i|$ in the atom \texttt{cp.norm(x, 1)} is replaced by variables $\Delta_i^+, \Delta_i^- \geq 0$ and the constraints $\Delta_i^+ - \Delta_i^- = x_i$.
The final reductions save the coefficients of the resulting problem into
the matrices and vectors of the standard form accepted by the solver. The
solver returns a solution of this standard-form problem, which CVXPY maps back to the original problem by inverting the
reductions. In
\Cref{sec:numerical-implementation}, we go through the implementation of the regularized joint 
optimization problem for Expected Shortfall \eqref{eq:joint_qp} and what these
steps generate for it.

\section{Numerical Implementation} \label{sec:numerical-implementation}

The programs derived in Appendices~\ref{app:es_derivation}--\ref{app:mad_derivation} are  written in CVXPY close to their mathematical formulations, and the
standard form passed to the solver is generated as described in \Cref{sec:cvxpy}. We showcase this for the
regularized joint optimization problem for Expected Shortfall \eqref{eq:joint_qp}. In the code, this program is written
as
\begin{equation} \label{eq:joint_es_cvxpy}
\begin{aligned}
    \bm{x}_t^*, \bm{\psi}_t^*, \alpha^*, \bm{u}^* = \argmin_{\bm{x}_t, \bm{\psi}_t, \alpha, \bm{u}} \quad
    & \alpha + \frac{1}{q(1-\beta)} \bm{1}_q^\top \bm{u}
    + \lambda_1^a \|\bm{x}_t\|_1 + \lambda_1^c \|\bm{\psi}_t\|_1 \\
    & + \lambda_2^a \|\bm{x}_t\|_2^2 + \lambda_2^c \|\bm{\psi}_t\|_2^2, \\[2pt]
    \text{s.t.} \quad
    & \bm{u} \ge -\bm{R}^{fh} \bm{x}_t - \bm{R}^c \bm{\psi}_t - \alpha \bm{1}_q, \quad \bm{u} \ge \bm{0}_q, \\
    & \bm{x}_t^\top \bm{1}_N = 1, \quad \|\bm{x}_t\|_1 \le \ell^a.
\end{aligned}
\end{equation}
As in \eqref{eq:joint_qp}, the Expected Shortfall is linearized with the auxiliary
variables $\bm{u}$ of \eqref{eq:slack_constraint}, but the penalties and the leverage constraint are kept as norms
instead of being split as in \eqref{eq:l1_decomp}.

\begin{lstlisting}[style=python, float=htbp, caption={Regularized joint Expected Shortfall program implementation in CVXPY.}, label={lst:joint-es}]
import cvxpy as cp

# Data and configuration.
beta, ell_a = 0.8, 2.0
q, N = R_fh.shape
M = R_c.shape[1]

# Variables.
x = cp.Variable(N)
psi = cp.Variable(M)
alpha = cp.Variable()
u = cp.Variable(q)

# Penalties as parameters.
lambda1_a, lambda2_a = cp.Parameter(nonneg=True), cp.Parameter(nonneg=True)
lambda1_c, lambda2_c = cp.Parameter(nonneg=True), cp.Parameter(nonneg=True)

# Objective and constraints.
es = alpha + cp.sum(u) / (q * (1 - beta))
penalty = (lambda1_a * cp.norm(x, 1) + lambda1_c * cp.norm(psi, 1)
           + lambda2_a * cp.sum_squares(x) + lambda2_c * cp.sum_squares(psi))
constraints = [
    u >= -R_fh @ x - R_c @ psi - alpha,
    u >= 0,
    cp.sum(x) == 1,
    cp.norm(x, 1) <= ell_a,
]
problem = cp.Problem(cp.Minimize(es + penalty), constraints)

# One setting of the hyperparameter grid is selected.
lambda1_a.value, lambda2_a.value = 5e-4, 0.03
lambda1_c.value, lambda2_c.value = 5e-5, 5e-5

# Solve.
problem.solve(solver=cp.GUROBI)
x_opt, psi_opt = x.value, psi.value
\end{lstlisting}

Lines 5 and 6 of \Cref{lst:joint-es} read the dimensions $q$, $N$, and $M$ from the return matrices $\bm{R}^{fh}$ and
$\bm{R}^c$, and lines 9--12 declare the variables $\bm{x}_t$, $\bm{\psi}_t$, $\alpha$, and $\bm{u}$. Lines 15 and 16 declare
the four penalties as parameters, whose values are set only after the problem is built. Line 19 is the Expected Shortfall term of
\eqref{eq:joint_es_cvxpy}, lines 20 and 21 are the $L^1$ and $L^2$ penalties, and lines 22--27 are the constraints, namely
the linearization of the Expected Shortfall in line 23, the non-negativity of $\bm{u}$ in line 24, the budget constraint in
line 25, and the leverage constraint in line 26. Line 28 combines the objective and the constraints into a problem. Lines
31 and 32 assign the penalties of one point of the hyperparameter grid. Finally, line 35 solves the problem with Gurobi, 
configured as in \Cref{lst:gurobi-config}, and line 36 reads out the solution. 

None of the matrices of \eqref{eq:joint_qp} are written in the code. When \texttt{problem.solve} is called, CVXPY carries
out the steps of \Cref{fig:cvxpy-chain}. The norms in lines 20 and 26 are replaced by the split of the weights into positive
and negative parts \eqref{eq:l1_decomp}, the variables are combined into one vector, which corresponds to the decision
vector $\tilde{\bm{\theta}}_t$ of \eqref{eq:joint_qp}, and the coefficients of the objective and the constraints are
combined into the vector of constants, the penalty matrix, and the constraint matrices, which take the form 
of $\tilde{\bm{c}}$, $\tilde{\bm{Q}}$, $\tilde{\bm{D}}$, $\tilde{\bm{E}}$, $\tilde{\bm{A}}$, and
$\tilde{\bm{b}}$ in \eqref{eq:joint_qp}. 

In the backtest, this program is solved at every rebalancing date for all 256 points of the hyperparameter grid (further details on hyperparameter 
selection can be found in 
Appendix~\ref{app:additional-results}). Since the grid points differ only in the penalties,
the problem of \Cref{lst:joint-es} does not have to be rebuilt for
each grid point. To speed up the runtime, we keep the problem of each window cached and, for every further grid
point, only assign the new penalties before calling \texttt{solve}. As a result, CVXPY compiles the problem only once
per window.
The cache holds two problems at a time, one for the estimation window, used by all grid points, and one for the
estimation and validation windows together, used for the final refit.

All programs are solved with Gurobi, a state-of-the-art solver for linear, quadratic, and second-order cone programs. 
The solver is configured to use the barrier method with tight convergence and
accuracy tolerances. The exact configuration is given in \Cref{lst:gurobi-config}.

\needspace{15\baselineskip}
\begin{lstlisting}[style=python, caption={Configuration of Gurobi for all programs.}, label={lst:gurobi-config}]
problem.solve(
    solver=cp.GUROBI,
    verbose=False,
    BarConvTol=1e-8,
    Method=2,
    ScaleFlag=0,
    AggFill=0,
    PreDual=1,
    Presolve=1,
    Threads=3,
    FeasibilityTol=1e-9,
    OptimalityTol=1e-9,
)
\end{lstlisting}

The configuration was kindly provided by Dr.\ Patrick Lucescu, who calibrated it on the same dataset as used in this thesis. 

\section{Computational Complexity and Performance}\label{sec:computational-complexity}

The size of the programs derived in Appendices~\ref{app:es_derivation}--\ref{app:mad_derivation} grows with the
investable universe in two ways. In the regularized programs, every asset weight and currency exposure is split 
into positive and negative parts, so the number of variables always grows linearly with the number of assets and
currencies. For all risk measures except variance, every observation of the lookback window adds one more auxiliary
variable and one constraint to the program. The second-order Expected Shortfall programs additionally 
have a second-order cone constraint, which makes them harder to solve than the linear or quadratic programs of the other measures.
The joint programs are the largest, since they optimize all asset weights and currency exposures at once, whereas
sequential optimization splits the problem into an asset program and a small currency program. 
Regularization hardly changes the size of a program, but it multiplies the number of programs solved
at every rebalancing date, since the regularized programs are solved for every point of the hyperparameter grid.

The backtests were run on the Euler cluster of ETH Zürich, each as one job with four CPU cores and Gurobi using three
threads, as described in \Cref{lst:gurobi-config}. The backtester implementation of \Cref{sec:backtesting-framework} logs a timestamp at the start of every rebalancing date. 
For each program, we average these step
times over all logged backtests. 

\Cref{fig:runtime-small,fig:runtime-medium,fig:runtime-large} show the step times at each rebalancing date for the
small, medium, and large universes. The times grow with the size of the universe, from about a minute per rebalancing
date for the regularized joint Expected Shortfall program in the small universe to about half an hour in the large
universe, and within each universe they rise over the backtest period as the number of assets in the investable
universe grows. The regularized programs are considerably slower than the unregularized ones, 
and the regularized joint programs are the slowest of all programs. Across the risk measures, the second-order
Expected Shortfall programs are computationally the most expensive, followed by the Expected Shortfall programs. The variance programs
are the cheapest in the small and medium universes, but their cost grows faster because the size of the covariance matrix grows quadratically with the number of assets. In the large universe they are solved as fast as the Expected Shortfall programs
but slower than the semi-variance and mean absolute deviation programs.

Without regularization, the joint and the overlay programs are similar in terms of computational cost. With regularization, the joint programs
are slower than the overlay programs, about twice as slow in the small universe and up to 14 times slower in the large
universe.
